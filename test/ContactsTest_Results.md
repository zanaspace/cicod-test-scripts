> [!WARNING]
> **This module now has 9 distinct confirmed defects (11 table rows — 2 issues each reproduced twice), across every scenario touched this session:**
> 1. The **Update Contact** form does not preload the contact's existing Country/State, and attempting to Save without re-selecting them **fails silently** — no error message, no toast, the modal simply stays open.
> 2. **Create Note** silently fails (no error, no persistence) if the "Call Driver" dropdown is left at its default — confirmed twice (fails without it, succeeds immediately once it's set).
> 3. Submitting **Create Ticket In Contact** returned a raw, unstyled **"Not Successful!"** response and force-logged the session out (redirected to a broken `site/login&authorize=...` URL) on **2 of 3 attempts this session** — but the ticket had actually been created successfully in the backend every time (visible on retry/reload). Not 100% reproducible, but frequent enough (~2/3) that it should be treated as a real, high-priority defect, not a rare fluke.
> 4. The **Contact view page never displays Prefix or Middle Name**, even though both are correctly saved (confirmed via the Update Contact modal, which does pre-fill them) — a display-only gap, not data loss. Website *does* display correctly, further down the same panel.
> 5. On the Create-Ticket form, a custom **"Check Box" field silently discards its checked state** — ticket detail shows "No data submitted" despite the box being checked at submit time.
> 6. The **"Would you like to assign this task right away?" checkbox has no effect** — checking it does not assign the task to anyone (`Assigned By` / `Task assigned to` remain blank).
> 7. Toggling the Create-Ticket **"Existing" contact checkbox on and back off destroys the auto-filled contact data** (First/Last/Phone/Email) and does not restore it — the only recovery is abandoning the form and reopening it fresh from the contact's Tasks tab.
> 8. **Create User is completely broken** (see the new `test/UsersTest_Results.md` report) — confirmed 2/2 attempts with fully valid data.
> 9. **NEW — Ticket creation silently fails for any Queue Type other than the tenant's original one.** After building a brand-new Queue Type carrying the exact Address/Attach File/Signature fields the script describes (via the Workflow module's form builder) and correctly granting the role explicit Create/View access to it, submitting a ticket against it **still silently fails** — clean redirect, no error, nothing persisted — while the pre-existing "PLANNING AND SCHEDULING" Queue Type continues to work fine for the same user in the same session. Confirmed 2/2 on the new Queue Type, immediately followed by 1/1 success on the original one, ruling out a session-wide issue.
> 10. **Minor deviation, not a defect**: the "Grant access" button shown right after finishing a new Workflow navigates to a Roles list that renders empty (Total Records: 5, 0 rows shown); the same page loads correctly when visited directly. Worth a look, but outside this report's scope — noted for whoever owns the Workflow module.
>
> The good news buried in defect #9: every field the script describes for this sub-flow — **Issues/Complain equivalent, House/Apartment number, Street, Address line 2, Country, State, City, Postal/Zip code, Attach File, and Signature** — was confirmed to exist, render correctly, and accept input exactly as scripted, once reached through a properly-configured Queue Type. The only remaining blocker is defect #9 itself.

## 4. Confirmed Defects

1. **Update Contact form does not preload Country/State, and silently fails to save.** Opening "Edit" on an existing contact shows "Select Country"/"Select State" placeholders instead of the contact's real saved values (nigeria/abuja). Attempting to Save (even when only an unrelated field like Organization was changed) produces no error and no success message — the edit is silently discarded.
2. **Create Note fails silently without a Call Driver selection.** The "Call Driver" dropdown in the note editor has no visible required-field indicator, but omitting it causes Save to silently no-op (no error, no persistence). Confirmed reproducible: fails every time it's omitted, succeeds every time it's set.
3. **Create Ticket In Contact frequently returns a broken raw error page and force-logs the user out**, even though the ticket was actually created successfully server-side. Observed on **2 of 3 attempts** this session — frequent enough that it should be treated as a real, high-priority defect rather than a rare fluke. The combination of "looks like total failure" + "actually succeeded" + "kills the session" is a serious trust/UX issue.
4. *(Related to #1)* The Country dropdown on the Update Contact modal is a select2 widget that did not open a searchable country list when clicked, unlike the equivalent Country field on the Create Ticket flow (which does support search) — suggesting the Update Contact modal's select2 initialization is broken or not wired to a data source at all.
5. **Contact view page never displays Prefix or Middle Name**, even though both are correctly saved (confirmed via Update Contact's pre-fill). Minor/cosmetic — data isn't lost, just invisible on the one screen a user would check it.
6. **Dynamic form-builder "Check Box" fields silently discard their checked state** on ticket submission — the ticket detail page reports "No data submitted" even when the box was visibly checked at submit time.
7. **"Would you like to assign this task right away?" has no effect.** Checking it before Create does not assign the resulting task to anyone.
8. **Toggling Create-Ticket's "Existing" contact checkbox on and back off permanently destroys the auto-filled contact linkage** (First Name/Last Name/Phone/Email all revert to blank) for that form instance, with no way to restore it short of abandoning and reopening the form.
9. **Ticket creation silently fails against any newly-created Queue Type, even with correct role access.** After building a new Queue Type specifically to reach the script's address/attach-file/signature fields, and correctly granting the test role Create/View access to it, submitting a ticket against it silently failed twice in a row (clean redirect, no error, nothing persisted) — while the pre-existing "PLANNING AND SCHEDULING" Queue Type succeeded immediately afterward in the same session. This points at something specific to newly-created Queue Types (missing default configuration, a required-but-hidden association, etc.), not a general regression.
10. **Create User is completely broken** — see [`test/UsersTest_Results.md`](UsersTest_Results.md) for the full write-up; confirmed 2/2 with fully valid data, no error shown.

## 5. Deviations (Not Bugs, But Worth a Note)

- Two forms with identical field placeholders coexist on the Contacts page (a hidden "Quick Actions" shortcut form and the real "Add Contact" form) — not a bug, but a trap for anyone scripting against placeholder text rather than form/element IDs.
- The Tasks-tab search box only live-filters on a `keyup` event, not a plain value/`input` change — real keyboard users are unaffected, but worth knowing for anyone automating or integrating with this field.
- Sidebar/menu labels this feature "Task", while the script and the contact-view button call it "Ticket" — consistent with the same Task/Ticket naming inconsistency already noted in the Workflow and Forms module reports.
- The "Grant access" button shown right after finishing a new Workflow navigates to a Roles list (`r=rightTemplate/index`) that rendered with 0 rows despite "Total Records: 5"; visiting the same URL directly rendered all 5 roles correctly. Worked around by navigating there directly instead. Worth a look by whoever owns the Workflow/Roles module, but out of scope for this report.

## 6. Suggested Improvements

### A. Fix priority
1. **P1 — Update Contact silent save failure**: likely the same root cause as the Country/State pre-fill bug (item #1/#4 above) — the update payload is probably sending empty `country_id`/`state_id` because the select2 widgets never got populated, and the backend either rejects it silently or the frontend never surfaces the rejection. Fix the pre-fill first, then confirm Save works end-to-end.
2. **P1 — Create Note silent failure without Call Driver**: either mark the field as visibly required (red asterisk, matching the pattern already used elsewhere in this same modal for other required fields) or relax the backend requirement if it isn't actually meant to be mandatory.
3. **P2 — Investigate the intermittent Create-Ticket "Not Successful!" + logout.** Since it succeeded on retry, this smells like a race condition or a stale CSRF/session token on the first submit after a specific page-load sequence — worth checking server logs around the two "UAT Ticket..." submissions from this session (17 Sep 2026) to correlate.
4. **P1 — Ticket creation silently fails on newly-created Queue Types.** Compare whatever backing record differs between the original "WORK BREADOWN STURCTURE" Queue Type and a fresh one like "UAT Address Signature Queue Type" (e.g., a missing default status transition, an unset internal flag, a workflow-engine registration step that only runs for queue types created through a different path). This blocks every brand-new workflow's tickets from ever being created, which is a severe defect for a paperless-workflow product.

### B. Test-script / coverage gaps
- The CONTACTS sheet should be split to remove the misplaced User-creation rows (or explicitly cross-referenced to the USER sheet) to avoid double-counting/coverage confusion in future UAT passes.
- No negative-path tests exist in the script for Create/Update Contact (e.g., invalid email format, invalid phone format) — worth adding given Users and other modules do have negative-path rows.
- The 17+ optional Create-Ticket-In-Contact fields (address auto-fill, file attach, e-signature) have no dedicated pass/fail rows of their own in the script; they're currently bundled into one generic step each. Given how deep that sub-form is, it would benefit from being broken out the same way the main Contact form's fields are.
