## 4. Confirmed Defects (Functional / UI)

1. **P0 — Public "Fill a Form" link never loads a form.** The `webform/<form-name>` URL generated by the Share feature shows "Unable To Load Form!" for every form tested, including a real pre-existing production form. This is the entire purpose of an External/Internal form and is completely non-functional.
2. **Form Type classification is broken everywhere it's used.** The "Form Type" grid column and the Internal Forms / External Forms tab filters do not reflect a form's actual saved type — every form appears "External" regardless of what was selected at creation (confirmed against a form independently verified as "Internal" via its own Update page).
3. **Double URL-encoding in Share Link/Embed.** Spaces in the form name are encoded twice (`%2520` instead of `%20`) in both the shareable link and the embed `<iframe>` snippet. Minor on its own, but worth fixing alongside defect #1 since both touch the same link-generation code path.

## 5. Deviations (Not Bugs, But Worth a Product Decision)

- Script implies 3 form types (Internal/External/Inter MDA); live UI offers 5 (adds Status, Data Capture) — confirm whether the script should be updated to match.
- Form-field placement is click-to-add, not drag-and-drop as literally scripted — same pattern already noted in the Workflow module; worth reconciling script wording once, for both modules.
- Selecting a Queue Type auto-populates form fields from the linked workflow — a good, working integration, but undocumented in the script.

## 6. Suggested Improvements

### A. Fix priority
1. **P0 — Public form-fill outage**: this should be the single highest priority fix across both the Workflow and Forms modules audited so far — it silently defeats the entire purpose of creating a form.
2. **P1 — Form Type classification**: audit whatever field/flag drives both the grid column and the tab filters; they're likely reading the wrong property or a value that's never actually being persisted correctly at creation time.
3. **P3 — Double-encoding on share links**: likely a single `encodeURIComponent` call being applied twice in the link-generation code.

### B. Test-script / coverage gaps
- A **negative test for the public fill link** (e.g., an expired/suspended form, or a malformed slug) doesn't exist in the script — worth adding once defect #1 is fixed, to confirm the correct error state is distinguishable from "form doesn't exist" vs. "form is suspended."
- **Concurrent form names**: what happens if two forms are created with the same name (which the public link appears to key off of, based on the `webform/<name>` URL pattern)? Untested and potentially ambiguous given the link isn't ID-based.
- **File attachment on the public form** (PDF/JPEG/XLS/PNG, per script row 82) was never reachable this session due to defect #1, but is worth a dedicated test once the public page loads, including a file-type/size rejection case.
- **Bulk actions** across forms (bulk suspend/share) are not scripted and don't appear to exist in the UI — confirm whether that's intentional.
