## 3. Confirmed Defects

1. **File Type filter dropdown is non-functional (Row 12)**: the button renders correctly on the Trash header toolbar, is enabled, and has no blocking CSS (`pointer-events: auto`), but clicking it produces zero observable effect — no dropdown panel, no ARIA state change, nothing added to the DOM. A user cannot filter trashed items by document classification at all in this build, despite the control being visibly present and inviting interaction.
2. **No manual "Delete Permanently" action exists anywhere (Rows 7 & 8)**: neither the per-row action menu nor any global toolbar button offers a way to permanently purge an item from Trash. This is either an intentional product decision (permanent deletion delegated entirely to the automatic 30-day retention sweep named in the banner) or a genuine gap versus the test script's expectations — worth a product/requirements confirmation either way, since as written it is a real functional absence relative to `TrashDocumentTest.md`.
3. **Properties inspector never activates for trashed items (Rows 9 & 10)**: single-click and double-click on a trashed file both leave the Properties panel on its default "There is no file selected" state, so file metadata (type, size, storage, owner, modified, created) is unavailable anywhere in the Trash view. This may be an intentional protection for soft-deleted items (consistent with the previous pass's characterization), but it does mean Row 10 of the script cannot be positively verified as passing.

## 4. Deviations (Not Bugs, But Worth a Note)

1. **Trash only ever contains files, never folders**, in every state observed this session — consistent with the My Documents finding that folders have no delete/trash action in the current UI. The script's Row 3 wording ("trash folders and files") may be stale relative to the live build.
2. **Row 5's action menu is reduced to a single item ("Restore File")** versus the script's example of "Restore, Delete Permanently" — this is the direct cause of Rows 7 and 8 being not-implemented rather than a separate issue.
3. **This session's throwaway "delete permanently" test file (`UAT_Trash_DeletePerm_<timestamp>.txt`) could not actually be permanently deleted**, precisely because of Confirmed Defect #2 above — it remains in Trash at the end of this session and will be purged automatically by the 30-day retention policy. This is expected fallout from the missing feature, not a new issue.

## 5. Suggested Improvements

### A. Fix priority
- **P1**: Investigate and fix the File Type filter dropdown (Row 12) — it is fully non-functional, not just visually reduced, which is more severe than a typical "reduced menu" deviation seen elsewhere in this test family.
- **P2**: Confirm with product whether "Delete Permanently" / "Empty Trash" are intentionally omitted (retention-policy-only deletion) or a genuine gap; if intentional, the test script should be updated to stop expecting them so future UAT passes don't keep flagging the same non-issue.
- **P3**: Consider whether the Properties panel should show at least basic metadata (name, size, date — already visible in the table) for a selected trashed item, since it currently shows nothing at all rather than a reduced/protected view.

### B. Test-script / coverage gaps
- **Test script (`test/TrashDocumentTest.md`) is stale relative to the live UI** in the same ways identified in `MyDocumentTest_Results.md`: it assumes a richer per-row menu (Delete Permanently) and a global bulk-purge flow (Empty Trash confirmation modal) that do not exist in the current build. Recommend a script refresh once product intent on permanent deletion is confirmed.
- **Not exercised**: filtering behavior itself (Row 12) could not be exercised beyond confirming the control is inert, since no dropdown ever appeared to select a file type from.
- **Historic Files, Departments, Collaborations, General/Application/ECMS/WFM Documents, Recent, Starred** sidebar destinations were not re-verified in this session — out of scope for `TrashDocumentTest.md` and already covered (or pending) in their own dedicated test files.
