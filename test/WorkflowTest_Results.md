## 3. Confirmed Defects (Functional / UI)

1. **Role-access grid renders empty.** `rightTemplate/index?grant-access=true` (reached via Finish → "Grant access") shows correct summary counts (5 total / 5 active / 0 suspended) but the table body has **zero rows**, even after a hard reload. There is no way to select a role and grant it access to a newly created workflow through this flow.
2. **Queue/Queue Type/Status tabs are not reload-safe.** Direct navigation or refresh on `?r=workflows/queue` (and, by construction, the Queue Type / Status equivalents) returns a generic "Oops! Something went wrong" error page. These views only function as client-side tab switches within an already-loaded `workflows/index` session.
3. **Row action menu on Queue/Queue Type/Status tabs shows the wrong menu.** Clicking the ⋮ action button on any row in these three tabs opens the **workflow-level** action menu (View/Unsuspend/Update workflow) instead of a row-appropriate menu (expected: Update, per script). This is reproducible on all three tabs and blocks roughly a third of the total script (Update Queue/Queue-Type/Status item, linked-status trigger/suspend/hide, status creation via link-statuses, and per-entity suspend).
4. **Department-linking is completely broken (P0).** Answering "Yes" to "link this workflow to a department" requires generating a CICOD/Gov Drive folder path, but that step permanently fails with "Session Expired" in its embedded panel — reproduced 3/3 times across two different queues (one brand-new, one long-established). The Folder Path field is disabled (no manual entry workaround), so **a workflow can never be saved while linked to a department**; the only way to finish creating a workflow today is to answer "No". See Section 6 for the full scenario.

## 4. Deviations (Not Bugs, But Worth a Product Decision)

- Script says tabs are "Forms/Escalations/Approvals" (plural); live UI uses "Form/Escalation/Approval" (singular) — cosmetic only.
- New Queue Types have **no default Open/Closed statuses**, contrary to the script's expectation — confirm whether defaults should be seeded automatically.
- Creating/selecting a Status does not update the closed dropdown's displayed text (no "Selected: X" or item count) even though the selection is saved correctly — a discoverability gap for users.
- Form-field placement is click-to-add, not drag-and-drop as literally scripted — a UX/spec mismatch worth reconciling in the next script revision.
- No persistent "Grant access" entry point exists on the Workflow Details → Roles tab; it is currently reachable only via the one-time post-creation prompt.

## 5. Suggested Improvements

### A. Fix priority (defects found this session)
1. **P0 — Department linking cannot complete**: "Generate Folder Path" is fully broken (embedded Gov Drive panel stuck on "Session Expired"), and the Folder Path field is disabled with no manual fallback. This blocks 100% of department-linked workflow creation, not just an edge case — recommend treating as the top priority of everything found in this report.
2. **P1 — Role grid empty state**: investigate why `rightTemplate/index?grant-access=true` returns the correct aggregate counts but no row data; this fully blocks the documented "give a role access to a workflow" journey.
3. **P1 — Wrong action menu on Queue/Queue Type/Status tabs**: the dropdown component appears to be a single shared instance that isn't reset/rebound when the user switches from "My workflows" to "Queue"/"Queue Type"/"Status" — audit the menu's state management (likely a shared ref/singleton bound to the last-rendered row).
4. **P2 — Reload-safety for sub-tab routes**: either make `?r=workflows/queue` (and siblings) resolve correctly on a cold load, or redirect them to `workflows/index` with the correct tab pre-selected instead of showing a generic error page.
5. **P3 — Default Open/Closed statuses**: decide and document whether new Queue Types should auto-seed default statuses, and align the test script to match whichever behavior is intended.
6. **P3 — Status-selection UI feedback**: show the selected status name (or a "N selected" count) in the closed dropdown after Create-and-Select, matching the behavior already present for Queue and Queue Type.

### B. Test-script / coverage gaps (additional scenarios worth adding)
- **Negative/validation cases** the script never covers: duplicate Queue/Queue-Type/Status names within the same scope; a Time Value of `0` or a negative number on an Escalation level; leaving "Who should the escalation/approval be sent to?" unselected and clicking Save.
- **Role + Department combination** for the "Role" escalation type (script mentions it but was not exercised this session because the Escalation flow was only run once, for Line Manager).
- **Approval routing correctness**: create an Approval level with distinct "Next Status After Approval" vs "Next Status After Rejection", then actually approve/reject a ticket and confirm it lands on the correct next status — this end-to-end outcome is never verified by the current script, only the configuration screen.
- **Multi-level escalation chains**: the script mentions "Add New Escalation Level" (a second level) but a full 2+-level chain was never verified end-to-end against actual ticket aging/time triggers.
- **Permission boundaries**: verify a non-admin role without "Workflow" feature access cannot reach `workflows/create` or `workflows/index` directly by URL.
- **Search/Filter/Sort** on the My Workflows, Queue, Queue Type, and Status tables — present in the UI (Search box, "Sort By", "Filter") but not scripted at all.
- **Bulk suspend** and **workflow deletion** (the script only ever suspends; there is no scripted case for permanently removing a workflow, queue, queue type, or status — confirm whether deletion is intentionally unsupported).

### C. Testability recommendation
This session's biggest time cost wasn't the CICOD product — it was **UI automation fragility**: duplicate elements with identical visible text (two "Next" buttons, one hidden), custom modals that don't use standard `.modal`/Bootstrap markup (requiring text-based DOM walks to locate the right container), and native `confirm()` dialogs that silently hang headless CDP sessions until explicitly handled. Recommend the team adopt `data-testid` attributes on primary interactive elements (buttons, tabs, row actions) and standardize on a single confirmation-dialog pattern (custom modal *or* native `confirm()`, not a mix) — this alone would make future regression automation dramatically more reliable and repeatable.
